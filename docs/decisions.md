# Принятые решения и ограничения

Документ описывает архитектурные решения, принятые при разработке прототипа сервиса генерации карточек товаров для B2B-магазина СОЮЗ-ПРИБОР, а также текущие ограничения и дорожную карту развития.

**Автор:** Бахимов Олег Николаевич
**Дата:** 13 ноября 2026 г.

## 1. Архитектурные решения

### 1.1. Выбор LLM-провайдера: RouterAI

**Решение:** подключение через российский AI-роутер [RouterAI.ru](https://routerai.ru) по OpenAI-совместимому протоколу.

**Обоснование:**

1. **Соответствие требованиям РФ:**
   - Серверы расположены в РФ (соответствие 152-ФЗ о персональных данных)
   - Включён в Реестр отечественного ПО № 35499 (от 05.10.2026)
   - Возможность работы по договору для юрлиц и ИП

2. **Финансовая логистика:**
   - Оплата в рублях российской картой
   - Оплата по счёту для юрлиц с закрывающими документами
   - Прозрачный биллинг с контролем расходов на уровне API-ключей

3. **Технические преимущества:**
   - OpenAI-совместимый API — смена модели = смена одного параметра `LLM_MODEL`
   - Автоматическая отказоустойчивость (переключение на резервного провайдера при недоступности основного)
   - Единый ключ для всех моделей (OpenAI, Anthropic, Google, DeepSeek)

**Альтернативы и причины отказа:**

| Альтернатива | Причина отказа |
|--------------|----------------|
| Прямой OpenAI API | Сложности с оплатой из РФ, серверы за рубежом |
| Anthropic API | Ограниченный доступ, проблемы с биллингом в РФ |
| Локальная модель через Ollama | Требует GPU, высокая стоимость инфраструктуры для прототипа |
| YandexGPT | Ограниченный контекст, менее качественная работа с техническими текстами |

### 1.2. Выбор модели: gpt-6.1-terra-pro

**Решение:** использование модели `openai/gpt-6.1-terra-pro` через RouterAI.

**Обоснование:**

- **Длина контекста:** достаточна для полного описания технических характеристик и генерации SEO-описания до 1200 символов
- **Качество русского языка:** оптимальное для B2B-контента контрольно-измерительных приборов
- **Предсказуемость:** низкая вариативность ответов при `TEMPERATURE=0.3`
- **Соотношение цена/качество:** приемлемая стоимость за токен при хорошем качестве

**Возможные альтернативы в RouterAI:**

- `anthropic/claude-sonnet-4-5` — выше качество, но дороже
- `google/gemini-2.5-pro` — дешевле, но хуже работает с русским
- `deepseek/deepseek-v4-pro` — самая дешёвая, но ниже качество

### 1.3. Фреймворк: FastAPI + Pydantic

**Решение:** FastAPI вместо Flask/Django.

**Обоснование:**

1. **Встроенная валидация** — Pydantic автоматически проверяет входные данные и возвращает 422 с описанием ошибки
2. **OpenAPI из коробки** — Swagger UI генерируется автоматически, не нужно писать документацию
3. **Асинхронность** — `asyncio` позволяет обрабатывать несколько запросов параллельно
4. **Строгая типизация** — снижение риска ошибок на этапе разработки
5. **Производительность** — один из самых быстрых Python-фреймворков

**Сравнение с альтернативами:**

| Критерий | FastAPI | Flask | Django |
|----------|---------|-------|--------|
| Валидация | Встроенная | Нужен `marshmallow` | Встроенная (формы) |
| Авто-документация | Да (Swagger + ReDoc) | Нет | Нет |
| Асинхронность | Из коробки | Частичная | Частичная |
| Overhead | Минимальный | Минимальный | Высокий |
| Скорость разработки | Высокая | Высокая | Средняя |

### 1.4. Структура промптов: двухуровневая

**Решение:** разделение на системный и пользовательский промпты.

**Обоснование:**

- **Системный промпт стабилен** — задаёт роль и ограничения, не меняется между запросами
- **Пользовательский промпт динамический** — шаблон с подстановкой данных конкретного товара
- **Разделение ответственности** — упрощает отладку: если ошибка в данных, смотрим пользовательский промпт; если в стиле — системный
- **Лёгкость A/B тестирования** — можно менять один из промптов без переписывания кода

## 2. Промпт-инжиниринг

### 2.1. Ключевые приёмы

#### 2.1.1. Защита от галлюцинаций

**Задача:** модель не должна выдумывать технические характеристики, которых нет во входных данных.

**Решение:** в системном промпте три жёстких ограничения:

**КРИТИЧЕСКИ ВАЖНО:**  

- НЕ ВЫДУМЫВАЙ технические характеристики, которых нет во входных данных
- Если характеристика отсутствует, используй маркер «данных нет»
- Все числовые значения бери ТОЛЬКО из входных данных


**Дополнительная защита:** низкий `TEMPERATURE=0.3` снижает креативность модели и делает ответы более предсказуемыми.

#### 2.1.2. Структурированный JSON-ответ

**Задача:** получить ответ в формате, который можно парсить без regex.

**Решение:**

- Явная инструкция «Верни ТОЛЬКО валидный JSON без markdown-обёрток»
- Описание структуры каждого поля в пользовательском промпте
- Двухуровневый парсинг: сначала `json.loads`, при неудаче — regex-поиск JSON-блока

#### 2.1.3. Примеры формата

**Задача:** модель должна понять ожидаемый формат каждого поля.

**Решение:** для критичных полей даны примеры:

- **SEO-заголовок:** «ПИД-регулятор ОВЕН ТРМ251 — RS-485 | СОЮЗ-ПРИБОР»
- **SEO-описание:** структура из 4 блоков (что это, возможности, применение, гарантия)
- **search_queries:** примеры коммерческих и информационных запросов

#### 2.1.4. Лимиты длины

**Задача:** контролировать объём генерации.

**Решение:** явные ограничения в промпте:

- SEO-заголовок: до 70 символов
- SEO-описание: 800–1200 символов
- Commercial-блок: 300–500 символов
- Search queries: 3–5 штук

#### 2.1.5. Разделение ролей

**Задача:** модель должна понимать контекст.

**Решение:** в системном промпте указана конкретная роль:

**Ты — контент-менеджер B2B-магазина контрольно-измерительных приборов.**


Это настраивает стиль ответа: технический, деловой, без маркетинговой «воды».

### 2.2. Параметры генерации

| Параметр | Значение | Обоснование |
|----------|----------|-------------|
| `TEMPERATURE` | 0.3 | Низкая креативность = меньше галлюцинаций и более предсказуемые ответы |
| `MAX_TOKENS` | 4096 | Достаточно для полного описания с учётом всех выходных полей |
| `max_retries` | 3 | Устойчивость к временным сбоям API без избыточных запросов |
| `retry_delay` | 2 сек × номер попытки | Экспоненциальная задержка снижает нагрузку на API |

### 2.3. Итерации промптов

В процессе разработки промпты прошли несколько итераций:

**Итерация 1:** простой промпт «сгенерируй карточку товара»
- Проблема: модель выдумывала характеристики, ответ не был структурированным

**Итерация 2:** добавлен запрет галлюцинаций
- Проблема: ответ всё ещё содержал markdown-обёртки, парсинг ломался

**Итерация 3:** требование JSON-only
- Проблема: модель иногда возвращала JSON с пояснениями до/после

**Итерация 4 (финальная):** двухуровневая структура + явные примеры + regex-фоллбэк в парсере
- Результат: стабильный парсинг, отсутствие галлюцинаций, предсказуемые ответы

## 3. Обработка ошибок

### 3.1. Уровни обработки

| Уровень | Реализация | Примеры ошибок |
|---------|------------|----------------|
| **Валидация входа** | Pydantic | Невалидный JSON, отсутствие обязательных полей |
| **Retry-логика** | LLMClient | Временные сбои API (429, 500, timeout) |
| **Критические ошибки** | LLMClient | Неверный ключ, отсутствие средств |
| **Парсинг ответа** | LLMClient._parse_json_response | Невалидный JSON от модели |
| **Обрезанный ответ** | Логирование | `finish_reason == "length"` |

### 3.2. Retry-логика

**Алгоритм:**

```python
for attempt in range(max_retries):      # 3 попытки
  try:
    response = call_llm()
  return parse(response)
  except Exception as e:
    if is_critical(e): # неверный ключ, нет средств
      break
    wait(retry_delay * (attempt + 1))   # 2, 4, 6 секунд
    return error_response
```

**Обоснование:** LLM API иногда возвращают временные ошибки. Три попытки с экспоненциальной задержкой покрывают 95% случаев временной недоступности без избыточной нагрузки.

### 3.3. Критические ошибки (без retry)

Ошибки, которые не имеют смысла повторять:

- `invalid_api_key` — неверный ключ
- `insufficient_quota` / `insufficient balance` — закончились средства
- `model_not_found` — модель недоступна
- `authentication` — проблемы с авторизацией

Для таких ошибок сразу возвращается 500 с описанием проблемы.

### 3.4. Парсинг JSON с фоллбэком

**Двухуровневая стратегия:**

1. **Прямой парсинг:** `json.loads(response)`
2. **Если не сработало:** regex-поиск JSON-блока `\{[\s\S]*\}` в тексте ответа
3. **Если и это не сработало:** `ValueError` с первыми 200 символами ответа для отладки

Это защищает от случаев, когда модель добавляет пояснения до/после JSON.

## 4. Безопасность

### 4.1. Хранение секретов

- **API-ключи только через переменные окружения** (`.env` файл)
- **`.env` в `.gitignore`** — секрет не попадает в репозиторий
- **`.env.example` как шаблон** — с плейсхолдерами вместо реальных ключей

### 4.2. Валидация входных данных

- **Pydantic-модели** проверяют все входные данные
- **Типизация полей** — нельзя передать строку вместо числа
- **Минимальные длины** — `name` не может быть короче 3 символов
- **Защита от инъекций** — данные не используются в SQL/raw commands

### 4.3. CORS

Для прототипа CORS открыт (`allow_origins=["*"]`). В production следует:

- Ограничить доменами 1С-Битрикс и административной панели
- Использовать `allow_credentials=True` только для конкретных доменов
- Добавить CSRF-токены для небезопасных методов

## 5. Ограничения прототипа

### 5.1. Текущие ограничения

| Ограничение | Влияние | Приоритет устранения |
|-------------|---------|---------------------|
| **Нет кэширования** | Повторные запросы тратят токены | Высокий |
| **Синхронная обработка** | Один товар за запрос, долгая обработка каталога | Высокий |
| **Нет аутентификации** | Эндпоинты открыты (допустимо для прототипа) | Средний |
| **Нет логирования в БД** | Нет истории генераций, нельзя анализировать качество | Средний |
| **Нет интеграции с 1С-Битрикс** | Контент-менеджер копирует результат вручную | Высокий |
| **Зависимость от внешнего API** | При недоступности RouterAI сервис не работает | Средний |
| **Нет веб-интерфейса** | Контент-менеджеры должны использовать Swagger | Средний |
| **Нет оценки качества** | Качество ответов не измеряется автоматически | Высокий |

### 5.2. Что не реализовано (согласно ТЗ)

Согласно разделу «Ограничения» ТЗ, в прототипе **намеренно не реализованы**:

- Полноценная CMS/административная панель
- База данных для хранения истории
- Деплой на production-сервер
- Конкретная интеграция с 1С-Битрикс
- Векторные базы данных и RAG

Эти функции оставлены для production-версии.

## 6. Дорожная карта развития

### Фаза 1: Базовая production-готовность (1 неделя)

**Цель:** подготовить сервис к использованию контент-менеджерами.

- [ ] **Пакетная генерация** для всего каталога из YML-фида СОЮЗ-ПРИБОР
- [ ] **Кэширование в Redis** — хранение результатов на 24 часа, экономия токенов
- [ ] **Экспорт в формат 1С-Битрикс** — CSV/JSON с полями, совместимыми с CMS
- [ ] **JWT-аутентификация** — защита эндпоинтов токенами
- [ ] **Логирование в PostgreSQL** — таблица `generations` с историей всех запросов

**Ожидаемый результат:** контент-менеджер может сгенерить карточки для 1000 товаров за 1 запуск.

### Фаза 2: Качество и удобство (1–2 недели)

**Цель:** повысить качество генерации и удобство использования.

- [ ] **LLM-as-Judge** — автоматическая оценка качества ответов по критериям:
  - Отсутствие галлюцинаций
  - Соответствие длины
  - Релевантность SEO-запросов
  - Полнота commercial-блока
- [ ] **Fine-tuning промптов** на основе обратной связи контент-менеджеров
- [ ] **Веб-интерфейс** — простая форма для контент-менеджеров (без Swagger)
  - Загрузка YML-фида
  - Предпросмотр результатов
  - Редактирование перед публикацией
- [ ] **Система рейтинга** — контент-менеджер оценивает качество каждой генерации

**Ожидаемый результат:** средняя оценка качества ≥ 4.5/5, время на ручную правку карточки ≤ 2 минут.

### Фаза 3: Интеграция и масштабируемость (до 1 месяца)

**Цель:** встроить сервис в существующую инфраструктуру СОЮЗ-ПРИБОР.

- [ ] **RAG-система** на базе:
  - Технической документации ОВЕН
  - Каталога СОЮЗ-ПРИБОР
  - Истории предыдущих карточек
- [ ] **Локальная модель через Ollama** — работа в замкнутом контуре (важно для B2B)
- [ ] **Автоматическая публикация в 1С-Битрикс** через REST API
- [ ] **Observability:**
  - Метрики Prometheus (latency, tokens, error rate)
  - Трейсинг Jaeger
  - Алертинг в Telegram при ошибках
- [ ] **Celery + RabbitMQ** для асинхронной обработки больших каталогов

**Ожидаемый результат:** 90% карточек генерируются и публикуются без участия человека.

### Фаза 4: Интеллектуальные функции (1-2 месяца)

**Цель:** расширить функционал за рамки генерации карточек.

- [ ] **ИИ-ассистент для подбора приборов** — отвечает на вопросы клиентов, помогает выбрать прибор под задачу
- [ ] **Мультиязычные карточки** — автоматический перевод на английский для экспорта
- [ ] **A/B-тестирование SEO-заголовков** — проверка, какие заголовки дают лучшую конверсию
- [ ] **Интеграция с CRM** — отслеживание конверсии карточек в продажи
- [ ] **Предиктивная аналитика** — рекомендация, какие товары требуют обновления описаний

**Ожидаемый результат:** сервис становится полноценным ИИ-ядром для e-commerce направления СОЮЗ-ПРИБОР.

## 9. Заключение

Разработанный прототип решает ключевую задачу ТЗ — **генерацию карточек товаров без выдумывания характеристик** — и демонстрирует возможность построения production-ready сервиса для СОЮЗ-ПРИБОР.

**Ключевые достижения прототипа:**

1. **Работающий MVP** с полным циклом: входные данные → LLM → структурированный результат
2. **Российская инфраструктура** — оплата в рублях, соответствие 152-ФЗ
3. **Защита от галлюцинаций** — модель не выдумывает технические характеристики

**Следующий шаг:** пилотное внедрение на части каталога СОЮЗ-ПРИБОР с оценкой реальной экономии времени контент-менеджеров и качества генерируемых карточек.
